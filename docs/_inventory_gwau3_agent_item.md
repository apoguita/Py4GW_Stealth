## How the classification was decided (the mechanisms these files actually use)

The ten modules never call a native address or synthesise input directly. They reach the game through
five helper families, all of which live outside the ten files:

| Helper | Definition | What it really does |
| --- | --- | --- |
| `Memory_Read($a_p_Address, $a_s_Type = 'dword')` | `API\Core\GwAu3_Core_Memory.au3:33-37` | `ReadProcessMemory` + `DllStructGetData`. Plain read; a failed read silently yields the zero-initialised struct value. |
| `Memory_Write($a_p_Address, $a_v_Data, $a_s_Type = 'dword')` | `GwAu3_Core_Memory.au3:27-31` | `WriteProcessMemory`. |
| `Memory_ReadPtr($a_p_Address, $a_ai_Offset, $a_s_Type = 'dword')` | `GwAu3_Core_Memory.au3:39-60` | Walks the offset chain with `ReadProcessMemory`; returns a 2-element array `[Ptr(finalAddress), value]`; returns `[0, 0]` the moment an intermediate dereference is 0. |
| `Core_Enqueue($a_p_Ptr, $a_i_Size)` | `GwAu3_Core.au3:559-566` | `WriteProcessMemory` of a command record into slot `$g_p_QueueBase + 256*$g_i_QueueCounter`, then advances `$g_i_QueueCounter`. The record's first dword is the address of an assembler label; the injected `MainProc` detour (`GwAu3_Core_Assembler.au3:1949-2030`, entered via the `MainStart` detour written at `1905`) reads the slot on the game's own thread and `jmp ebx`s into that label (`2004-2009`), which `call`s the native. So the enqueue is a **game-thread call**, staged through process memory. |
| `Core_SendPacket($a_i_Size, $a_i_Header, $a_i_Param1..$a_i_Param10 = 0)` | `GwAu3_Core.au3:575-589` | Fills `$g_d_Packet` and enqueues it as `CommandPacketSend` (label at `GwAu3_Core_Assembler.au3:2088-2099`), whose body `call PacketSend` with `PacketLocation` and the header/payload. Server-bound packet. |

Two further helpers matter only for the decode paths:

| Helper | Definition | What it really does |
| --- | --- | --- |
| `Utils_DecodeEncString($a_p_Ptr)` | `API\Core\GwAu3_Core_Utils.au3:440-462` | Reads `word`s out of game memory and folds them into an integer **string ID**. Despite the name it returns a number, not text. Returns 0 for a null pointer. |
| `Utils_DecodeEncStringAsync($a_p_Ptr, $a_i_Timeout = 1000)` | `GwAu3_Core_Utils.au3:469-498` | Reads the encoded `wchar[128]` out of game memory, `Memory_Write`s the ready flag to 0, `Core_Enqueue`s `$g_p_DecodeEncString`, then polls `$g_p_DecodeReady` and reads the client's output buffer. Host-side it is a read; the decode itself is the client's own routine, so the whole call is a **game-thread call**. |
| `Utils_DecodeStringID($a_i_StringID, $a_i_Timeout = 1000)` | `GwAu3_Core_Utils.au3:349-378` | Same enqueue/poll shape, for a numeric string ID. |
| `Utils_SkillDecodeStringID($a_i_StringID, $a_i_Timeout = 1000)` | `GwAu3_Core_Utils.au3:386-...` | Same, with skill argument placeholders appended. |

`World_GetWorldInfo` (`Data\GwAu3_Data_World.au3:10`) and `Game_GetGameInfo` (`Data\GwAu3_Data_Game.au3:10`)
are plain memory reads through `$g_p_BasePointer` context walks (`World_GetWorldContextPtr`, `GwAu3_Data_World.au3:4-8`).

Two consequences that apply throughout, and are the reason some rows carry a second spelling of the
classification:

1. `Core_SendPacket` and `Core_Enqueue` contain **no `Return` statement**. Every `Return Core_SendPacket(...)`
   and `Return Core_Enqueue(...)` in these modules therefore returns 0, never a meaningful value.
2. Several "read" functions are not read-only: the `"Name"`-style cases drive the client's decoder
   (game-thread call), and `Agent_ResetTargetRejectStats`, `Item_CanIdentifyAll`, `Item_IdentifyAll`,
   `Item_CanDepositAllMaterials`, `Item_DepositAllMaterials` and `Merchant_ClearTraderQuote` write into
   process memory.

There is **no UI/input synthesis anywhere in the ten files**: a scan for `ControlSend`, `keybd_event`,
`mouse_event`, `PostMessage`, `SendMessage`, `WinActivate` over all ten returns nothing. The only
`DllCall`s in the ten files are `ReadProcessMemory` (Agent array, Item arrays, Merchant scans) and one
`GetTickCount` (`Data\GwAu3_Data_Skill.au3:12`) — none target a game address, so no function in scope is
a `DllCall`-on-in-game-address game-thread call.

## What could not be classified cleanly

Nothing in scope was left without a classification, but four groups are genuinely ambiguous, and the
lines that make them so are these:

1. **`_ApplyFilters` (`Data_Agent:1221`)** — `Call($l_s_FilterName, $a_p_Agent)` (L1235) invokes whatever
   function the caller names in a string, with `-` prefix inversion (L1230-1237). Classified
   **PURE COMPUTATION** because the function itself performs no game access, but its effect is the
   effect of the named filter, which in this checkout is normally a memory read.
2. **`Agent_ConvertID` (`Data_Agent:3`)** and **`Item_ItemID` (`Data_Item:519`)** — the classification
   depends on the *argument type*, not on the function: pointer arguments are **MEMORY READ**
   (`Data_Agent:10`, `Data_Item:521`), DllStruct arguments are **PURE** (host-side
   `DllStructGetData`, `Data_Agent:12`, `Data_Item:523`), scalars are **PURE** (L14, L525).
3. **The string/name keys** — `Agent_GetAgentInfo "Name"`, `Agent_GetNpcInfo "Name"`,
   `Item_GetItemInfoByPtr "*Name"`, `Skill_GetSkillInfo` string keys. Each is a read function whose one
   key performs a game-thread call (`Data_Agent:518`, `Data_Agent:1003`, `Data_Item:643/655/662`,
   `Data_Skill:152/155/158/162/167`). A per-function label cannot express that, so the primary class is
   the read and the game-thread path is listed in the second-mechanism table.
4. **Four item functions and one agent function write a sentinel and then enqueue**
   (`Cmd_Item:304/305`, `322/323`, `340/341`, `358/359`) — the `Memory_Write` is a prerequisite of the
   `Core_Enqueue`, not a competing classification, but neither label alone is complete.

Two behaviours are recorded as **dead or inconsistent code**, not as classification problems:
`Agent_GetPlayerLogInfo`'s `"LastPartyHenchmenCount"` case (L1078-1080) computes a value and never
returns it, and `Skill_GetHexConditionRemovalHeal` (L874-882) builds `$i_Flags` (L875-876) that the
return expression at L879-881 never uses.
